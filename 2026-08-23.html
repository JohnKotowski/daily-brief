The new MCP roadmap: async agents, registries, and a stricter spec MCP Blog · HN 204 The Model Context Protocol team lays out where the standard goes next — and it reads like an admission that today's tool-calling model doesn't survive long-running agents.

The MCP maintainers published their forward roadmap, and the interesting parts are the gaps they're conceding. Long-running and asynchronous agent work is the headline: the current request/response shape assumes a tool call returns while the model waits, which falls apart the moment an agent kicks off a job measured in minutes or hours. Alongside that sit server registries and discovery (so agents can find capabilities rather than have them hand-wired), plus tighter spec conformance to stop the ecosystem fragmenting into mutually incompatible "MCP-ish" servers. For anyone building on MCP — and Morgan's own tool surface is exactly that — this is the clearest signal yet about which integration patterns are about to become load-bearing versus which ones are stopgaps.

Why your local LLM feels dumber than it is Level1Techs · HN 335 Most self-hosted disappointment isn't the model — it's quantisation, truncated context windows, and default sampler settings silently sabotaging output.

A detailed teardown of why the same open-weight model that benchmarks well feels markedly worse on someone's own hardware. The culprits are almost never the weights: aggressive quantisation applied to the wrong layers, context windows silently truncated by the serving layer well below the advertised limit, and sampler defaults (temperature, top-p, repetition penalty) inherited from tooling that was tuned for a different model family. The piece is practical rather than theoretical — it walks through how to check each failure mode. Worth reading if you've ever concluded "open models just aren't there yet" from a local test, because there's a good chance you were benchmarking your config rather than the model.

Debian developers vote on banning AI-assisted contributions Slashdot Eight competing proposals, from a hard ban to full permissiveness — the first major distro to put AI-generated code to a formal project-wide ballot.

Debian is running a General Resolution with eight ballot options on whether and how to restrict AI-assisted contributions, ranging from an outright prohibition to explicit permission with disclosure requirements. It matters beyond Debian because the project's governance is deliberately slow, consensus-driven, and heavily documented — whatever it lands on becomes the reference position other open-source projects cite. The hard question underneath is provenance: Debian's licensing guarantees depend on knowing where code came from, and a model's training corpus makes that claim unverifiable in a way that copy-pasted snippets never quite did. Expect the outcome to shape contributor policy across the Linux ecosystem well into 2027.
